Running PMS

How to run the system on your computer from VS Code, how to look at its backend, how changes reach the live site, and what each part of PMS does. PMS was previously called OmniTrack. This edition covers the move to Postgres and upgrade Phases 0 to 5 (November 2026).

1. How the system is put together

PMS has three parts. The screens are in project-management-system-frontend; the API, database migrations and deployment are in project-management-system-backend.

PartWhat it doesWhere it is
Screens (frontend)What people see in the browser: dashboard, projects, work items, boards, backlog and timeline, search, the service desk, feature requests, Concept Notes, reports and settings. Built with React and TypeScript.frontend/src/
API (backend)Handles every request under /api. All permission and visibility checks happen here. Runs as a Cloudflare Worker, with an hourly scheduled job.frontend/worker/ (section 8 lists the files)
DatabasePostgres on Neon (project wild-sunset-31993352). The branch production is the live database; the branch dev is for testing on your computer. The Worker reaches it through Cloudflare Hyperdrive (config pulse-db).project-management-system-backend/database/migrations/ (table structure, numbered in order)

Live site: https://pulse.utsa--wanza--ortfolio.workers.dev

The old address (omni-tracker.utsa--wanza--ortfolio.workers.dev) redirects there, keeping view-only links and project pages.

When you run the system on your computer, it uses the Neon dev branch, never the live database. Nothing you do locally changes the live site or its users. One exception: Ask AI always uses Cloudflare's live AI service, even locally, and that usage counts towards the account.

The two Cloudflare Workers

WorkerWhat it doesHow it is deployed
pulseProvides the web address and passes every request to the app Worker. It holds nothing else.By hand, rarely:
npx wrangler@4 deploy --config gateway/wrangler.jsonc
omni-trackerThe app itself: screens, API, the database connection, AI, the hourly job and the MFA_KEY secret. It keeps its old name on purpose. Smart Placement runs it close to the database.Automatically, on every push to the main branch, after the unit tests pass.
Do not rename, delete or replace the omni-tracker Worker, and do not change its MFA_KEY secret. The key encrypts everyone's authenticator-app codes, and it also seals the email key, the Teams webhook, the GitHub secret and every outbound webhook's signing secret. None of these can be read back. If the key is lost, every authenticator-app user needs an administrator reset, and email, Teams, GitHub and webhooks must all be set up again.

The old Cloudflare D1 database is still attached to the Worker as D1, read-only, as history. PMS stopped using it when it moved to Postgres.

The hourly job

The Worker has one scheduled trigger, every hour on the hour (0 * * * *). The Cloudflare account is on Workers Free, which allows only five cron triggers across all its Workers, so PMS uses one and works out what is due (frontend/worker/schedule.ts):

When (Harare time)What runs
Every hourSaved-filter email subscriptions, scheduled automation rules, service desk SLA warnings and breach alerts, and retries of failed outbound webhooks.
Weekdays at 07:00The data retention clean-up and the daily digests.
Mondays at 08:00The Monday Briefing.

2. Before you start (one time only)

  1. Install Node.js (version 22 or newer) from nodejs.org. To check it worked, open a terminal and run:
    node -v
  2. Install VS Code and open the project folder (File > Open Folder, then pick the project folder).
  3. Open the terminal in VS Code: press Ctrl + ` (the backtick key, left of 1), or use Terminal > New Terminal. Then install the packages:
    cd project-management-system-frontend
npm install
cd ../project-management-system-backend
npm install
  4. Create a file called project-management-system-backend/.dev.vars with these lines. It is never committed, and its values are never printed or shared:
    LineWhat it is
    PG_DEV=The connection string of the Neon dev branch (Neon console > the project > branch dev > Connect). Used by npm run dev:api.
    PG_MAIN=The connection string of the Neon production branch. Only needed by whoever applies migrations or takes backups of the live database.
    MFA_KEY=Any long random text, for your local copy only. Without it, two-step verification and sealed secrets won't work locally.
    QA_PASSWORD=The password of the test accounts on the dev branch (qa-admin, qa-dev, qa-viewer), for Postman and the checks.

Run npm install again only if the packages change (for example after pulling someone else's work).

3. Run the system: quick way

Use this when you just want to use or demonstrate the system.

  1. In the VS Code terminal, run:
    cd project-management-system-backend
npm run dev:api
  2. This builds the app, applies any new migrations to the Neon dev branch, and starts the backend. Wait until the terminal says it is Ready.
  3. Open http://localhost:8787 in your browser and sign in.

This mode doesn't pick up code changes while it's running. Stop it and run it again to see your edits.

To try the hourly job locally, start it with npm run dev:api -- --test-scheduled, then trigger a run from another terminal:
curl -X POST "http://127.0.0.1:8787/cdn-cgi/local/explorer/api/local/scheduled?worker=omni-tracker" -H "content-type: application/json" -d "{\"cron\":\"0 * * * *\"}"

4. Run the system: development way

Use this when you are changing the code. Screen changes show up the moment you save a file. You need two terminals: click the + or the split button in the terminal panel to open the second one.

The screens on port 5173 pass every /api request to the backend on port 8787, so both terminals must be running.

Locally, every database query travels to Neon in Singapore, so pages are much slower than on the live site (where the Worker runs next to the database). Creating a work item can take 20 to 30 seconds locally. That's normal.

5. Stopping and signing in

To stop: click into the terminal and press Ctrl + C. Do this in each terminal you started. On Windows a background workerd process can survive; if port 8787 stays busy, close VS Code completely, or end workerd.exe in Task Manager.

Signing in locally: the dev branch has its own accounts, including the test accounts qa-admin, qa-dev and qa-viewer (password in QA_PASSWORD). Their passwords may differ from the live site.

Passkeys belong to the web address they were added on. A passkey added on the live site doesn't work locally, and the other way round.

Who sees what

One rule decides who may see a work item, everywhere it appears: lists, item pages, boards, the timeline, reports, search, dashboards, subscriptions, digests, notifications, Ask AI, view-only links, the API, webhooks and automation (frontend/worker/access.ts).

  • Developers without "Log and assign feature requests" see only the items and feature requests assigned to them or that they reported, and only their own Concept Notes.
  • Security levels: an item with a level (such as "Confidential – Managers only" or "HR only") is seen only by administrators, its assignee and reporter, and the roles and people the level names.
  • View-only links are read-only, never see contact details, documents or items with a security level, and can't use search, the service desk or the API.
  • The service desk portal shows customers only their own requests and the replies marked for them; never internal notes or other items.

Setting up the service desk

  1. In Settings > Administration > Service desk, choose the project requests land in. An empty project is best: it takes the Service desk workflow (To Do, In Progress, Waiting for customer, Change Approval, Resolved, Closed), and the choice is refused if the project has items in other statuses. Until a project is chosen, the portal is closed.
  2. Check the request types (Incident, Service request, Change, Question), their questions and SLA targets, and the public holidays (Zimbabwe's 2026 and 2027 are filled in; add each new year's).
  3. Make a portal link for each client or site, and send it to them. Staff raise requests from Service desk > Raise a request.
  4. Customers hear about replies and status changes by email once email is connected in Email & Teams.

SLA clocks count business hours: Monday to Friday, 08:00 to 17:00 Harare time, less holidays and time spent waiting for the customer. They warn at 75% of a target and alert on a breach. A Change can only be resolved through Change Approval, which a Manager approves.

Connecting other systems

  • GitHub: Settings > Administration > Integrations has the steps. Commits, branches and pull requests that mention a key appear in the item's Development panel.
  • The API: each person makes their own token in Settings > Security & privacy > API tokens. A token acts as its owner. The full reference is docs/API.md.
  • Webhooks: PMS can post work item events to another system, signed with HMAC-SHA256. Set them up in Integrations.

D. Inside the app

Settings > Administration > Activity log shows who signed in, failed sign-ins and every change, filtered by kind (sign-ins, work items, workflows, sprints, filters and dashboards, automation, integrations and API, schemes, service desk, and more). Changes made with an API token are marked with the token's name; changes made by automation or through the portal are named as such.

9. Putting changes live

  1. Make and test your change locally (sections 4 and 7).
  2. If the change adds a file to project-management-system-backend/database/migrations/, release in this order:
    1. Back up the live database to a file, and check it isn't empty:
      node scripts/db.mjs backup main ../backup-before-<change>.sql
    2. Make a restore point in Neon: a branch of production called backup-before-<change> (Neon console > Branches > New branch, or the Neon CLI with --no-compute).
    3. Apply the migration to the live database:
      npm run db:migrate
  3. Commit and push to the main branch:
    git add .
git commit -m "Describe the change"
git push
  4. GitHub Actions runs the unit tests, builds the app and deploys it, usually within two minutes. Watch the Actions tab until it shows a green tick, then check the live site.
Migrations come first. The automatic deploy doesn't apply them, and the live site fails on a new column until it's applied. Backup files (backup-*.sql), .dev.vars, .env* and .neon must never be committed; .gitignore already leaves them out.

If something fails, stop and don't try fixes on the live database. The restore points are the backup file (restore by migrating an empty database and running the file) and the Neon branch (Neon can restore production from it). The restore points so far are backup-before-phase-0 to backup-before-phase-5.

If an automatic deploy fails with a Cloudflare error, run it again from the Actions tab. If it keeps failing, deploy from your computer from the project-management-system-backend folder with npm run deploy.

Adding a cron trigger: don't. The account is at the Workers Free limit of five cron triggers; add new scheduled work to src/schedule.ts and the hourly job instead.
